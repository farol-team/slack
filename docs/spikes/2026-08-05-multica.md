# Spike — Multica (`multica-ai/multica`)

**Date:** 2026-08-05 · **Method:** repository cloned and read (README,
LICENSE, `CLI_AND_DAEMON.md`, `server/internal/integrations/slack/*`,
`server/internal/daemon/*`, migrations, `skills-lock.json`). Claims below are
from the source unless marked as marketing.

## What it is

"The open-source managed agents platform. Turn coding agents into real
teammates — assign tasks, track progress, compound skills." A task board where
an agent is an assignee like a person: it picks up issues, comments, files
issues, reports blockers.

Repo signals: 44,248 stars, 5,611 forks, created 2026-01-13, still pushed
daily. Go backend (226+ migrations), TypeScript front end as a pnpm/turbo
monorepo with **web, desktop and mobile** apps. ~97 MB checked out.

Features that matter to us:

- **Squads** — agents grouped under a leader agent that delegates, so routing
  survives team growth (`@FrontendTeam`, not a named human).
- **Autopilots** — cron, webhook or manual triggers that create the issue and
  route it automatically. Standups, weekly reports, periodic audits.
- **Skills** — reusable procedural know-how with a lock file
  (`skills-lock.json` pins `anthropics/skills`, `shadcn/ui`,
  `vercel-labs/agent-skills` by content hash), like package pinning.
- **Unified runtimes** — local daemons *and* cloud runtimes in one dashboard.
- **15+ agent CLIs** — Claude Code, Codex, Copilot CLI, OpenCode, Cursor
  Agent, Kimi, Qoder, Trae, Grok, Qwen — most of them **over ACP**, the same
  protocol we speak.

## The overlap is close to total

`server/internal/integrations/slack` is ~5,700 lines and implements our path.
The addressing rule matches ours almost word for word: in a group the bot
answers only an explicit `<@bot>` mention, a DM ingests every message, and the
bot's own and other bots' events are dropped as a loop guard
(`inbound.go`). Slack sits behind a platform-neutral `channel` abstraction
next to Lark/Feishu and web; migration `131_issue_origin_slack_chat` turns a
Slack conversation into an issue; the agent can pull thread history through
`multica chat history` (`history.go`, paged, capped at 50 messages so a pull
cannot flood the agent's context).

So "mention in Slack → task runs on a local machine → result streams back" is
their feature too. The difference is that Slack is one of their doors, and it
is our entire product.

## Same problem, different answers

| | Multica | Farol |
|---|---|---|
| Transport to the machine | daemon **polls** every 3s, heartbeat 15s | push over wss, no open ports |
| Work directory | **git worktree per task** off a shared bare clone, GC with TTLs | one directory per channel |
| Routing | daemons **claim** tasks from the workspace queue | BYOA — only the mention author's runner |
| Permissions | headless runs use **`--yolo` / bypass permissions** | Approve/Deny buttons in Slack |
| Memory | skills: procedural, pulled from GitHub, hash-pinned | OpenViking: episodic channel archive, gateway-scoped |
| Client upgrades | `auto_update.go`, `multica update` | manual rebuild and reinstall |
| Adapter health | probing + path self-heal (`agents_probe.go`) | `is_installed` check only |

Our transport is the better design of the two: a push beats a three-second
poll on both latency and server load. The other rows do not favour us — see
[runner gaps](2026-08-05-runner-gaps.md).

## Licence — read before borrowing

Not Apache, despite looking like it. The "Multica License" is Apache 2.0 plus
conditions, of which one matters to us:

> you may not use the Multica source code to provide a hosted service to third
> parties, or embed Multica as a component of a product or service that is
> sold… Providing a hosted service to third parties is restricted **whether or
> not you charge for it**.

Internal use inside one organisation is free. A public instance for anyone
outside it needs a commercial licence even when it is free of charge. There
are also branding-retention conditions for their UI code and attribution
conditions for backend/daemon/CLI use.

**Practical consequence: we cannot take the code.** Farol is a hosted service
for other people's teams. Ideas are not licensable; source is.

## So what

Feature parity is not available — they have a mobile app and fifteen adapters;
we have three pinned ones. What is available:

- **Episodic team memory is a genuinely different axis.** Their skills answer
  "how do we deploy"; our memory answers "what is this channel about and how
  does this team talk". The second is what the non-engineers in the thread are
  paying for.
- **Human in the loop is a feature, not friction.** They run agents with
  permissions bypassed. For a team letting an agent into a production
  repository, our Approve/Deny is the reason security says yes — provided the
  button appears only where a wrong answer costs something (which is why
  memory calls stopped asking, see `session.rs::auto_allowed`).
- **The thread is the unit of work.** They ship a board, issues, assignees and
  squads — Jira with agents, and it has to be adopted. We have a conversation.
  For a team of five that is an advantage, not a gap.

The question to answer before the first paying customer asks it: **why pay us
when Multica is free and self-hostable?** Honest answers are "nothing to
operate", "memory that works out of the box" and "Slack is the product, not
one of the doors". "More features" is not an available answer.
