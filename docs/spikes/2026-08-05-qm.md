# Spike: qm — the hosted answer to the question we answer locally

**Date:** 2026-08-05. **Source:** `github.com/yc-software/qm` cloned at commit
`0f0e0ad` (2026-08-05, MIT, TypeScript, ~76k lines across 346 files in `src/`,
11.6k stars at the time of reading). Read-only source reading; qm was not run.

**Question:** qm is a Slack-first agent product built on the opposite premise —
agents run on the vendor's machines, not the user's. What does it do that we
should copy, and what does its existence say about our bet?

WorkRoom holds a deeper read of qm's sandbox layer
(`~/src/workroom/docs/spikes/qm-sandbox.md`, snapshot 2026-07-31). This spike
does not repeat it; it reads qm from Farol's angle — Slack surface, agent
harness, memory, and the hosted-runner question we raised today.

## What it is (observed)

Its own README: "A multiplayer agent harness for work. In Slack and on the
web." Architecture diagram: a headless core (API, identity, policy, scheduler)
plus an agent loop, Postgres for sessions/memory/queue, and a **per-scope
sandbox** holding files, tools and logged-in services.

Scopes are the organising idea (`src/types.ts:12`): `personal`, `channel`,
`team`, `org`, `group`. Each carries its own memory, files, keychain view,
permissions, crons and sandbox. A person's agent and a channel's agent are
different scopes over one deployment.

## The five things worth taking

**1. Reactions as the acknowledgement channel — with a twist.**
`src/slack/ack-emoji.ts` picks an ack emoji per message, refreshes the
workspace's custom emoji list hourly (`ACK_EMOJI_TTL_MS`), and keeps a
`COMPLETION_EMOJI` regex (`check|done|complete|approved|ship|tada|…`) to tell
completion marks from decoration. We shipped 👀/✅ today; qm's addition is
that it *asks the model* for a fitting emoji from the workspace's own set,
which is a small, cheap piece of personality we could copy without new scopes.

**2. Four approval modes, not two.**
`src/slack/approval-cards.ts:5` — `hilo_allow_once`, `hilo_allow_session`,
`hilo_allow_always`, `hilo_deny`, with per-request suppression of the session
and always variants. Ours is Approve / Deny / Stop. "Allow session" is the
missing middle: a person granting the same permission six times in one task is
the failure mode we will hit as soon as anyone does real work.

**3. Approvals move to a DM when the channel is the wrong room.**
Same file, line 45: a `toDm: true` path with the channel message reduced to a
pointer — "I sent you a DM to approve before I run that." We have no notion of
"this decision is yours alone" yet, and our permission cards sit in the channel
for everyone to see.

**4. Harness-agnostic by construction.** `src/harness/` carries
`claude-harness.ts`, `codex-harness.ts`, `opencode-harness.ts`, `pi-harness.ts`,
a `harness-router.ts` and a `mock-harness.ts`. Claude is driven as a spawned
process over stdio pipes (`spawnClaudeProcess`, `claude-harness.ts:133`);
OpenCode is driven over **HTTP against a local server** the harness starts and
discovers by parsing "opencode server listening … on <url>"
(`opencode-harness.ts:321`). Two observations follow. Their per-vendor code is
substantial because each vendor is integrated natively — where we get the same
plurality from ACP for a fraction of the code. And `mock-harness.ts` is the
piece we keep saying we need: a fake agent to test the loop without a model.

**5. Egress is default-deny, at the network.** `deploy/egress-proxy/envoy.yaml`
is an Envoy config with an embedded policy and "the unconditional
metadata/link-local deny"; sandboxes reach it via `HTTPS_PROXY` at a private
address (`fly.toml:3`). If we ever host runners, this is the shape: not "the
agent promises not to", but a proxy that refuses.

## Where it stands opposite us

| | qm | Farol |
|---|---|---|
| Where the agent runs | vendor's sandbox, per scope | the author's own machine |
| Whose model credentials | the deployment's | the developer's own subscription |
| Where the code is | cloned into the sandbox | already checked out, with their branches |
| Isolation problem | theirs to solve (three backends, egress proxy) | the OS the person already trusts |
| Onboarding | install one Slack app | install a Slack app **and** a desktop app |

The sandbox layer is where the cost of their choice shows: `src/sandbox/` holds
a capability-probed interface plus three backends — local Docker, AWS microVM
(`aws-microvm-api.ts` speaks an image/microvm/auth-token API directly), and
"sprites" — with routing rows so a scope can be migrated between substrates
(`sandbox-routing.ts`), plus tar staging, process sessions, and idle reaping.
That is the bill for "the agent lives on our machines", and it is the bill we
have not paid because we do not.

**Inference, not observation:** their per-scope durable sandbox is what lets
them promise personal customisation ("people customize the agent to be theirs")
without a second install. Our equivalent promise costs the user a download —
which is precisely the friction we watched today, and precisely the reason the
hosted-runner question came up.

## Their Slack surface, next to ours

qm asks for **22 bot scopes** against our 14. The ones we do not have:
`channels:manage`, `groups:write`, `chat:write.customize`, `emoji:read`,
`files:write`, `mpim:history/read/write`, `reactions:read`. Its 9 events
against our 5 add `member_joined_channel`, `member_left_channel`,
`message.mpim`, `reaction_added`, `reaction_removed`.

Read as a map of features: group DMs are a first-class room (`mpim:*`),
reactions are an input as well as an output (`reactions:read` +
`reaction_added`), the bot notices people joining and leaving channels, and it
writes files back (`files:write`). We deliberately skipped `reaction_added` and
`file_shared` today for want of a handler — qm has the handlers.

`chat:write.customize` is the one I would not copy: it lets a bot post under a
different name and avatar, and for an agent that acts on someone's behalf that
is a footgun in a product where provenance matters.

## What it changes for us

1. **"Allow session" is a gap, not a nicety.** Our Approve/Deny pair will make
   real work unbearable on the first task that touches ten files. Adding a
   session-scoped grant is a small change to `PermissionDecision` and the
   pending-permission map, and it should land before anyone tries a serious
   task through Slack.
2. **A mock harness earns its keep.** `runner/README.md` has listed "a mock ACP
   agent + a mock cloud" as future work since the start; qm keeping a
   `mock-harness.ts` beside four real ones is evidence it is not a luxury. Our
   entire agent path is currently untested.
3. **The hosted-runner design has a reference implementation.** If we take the
   split we discussed (hosted for memory questions, local for code), qm shows
   the parts we would still need: an egress proxy with default-deny, per-scope
   durable state, and a routing table so a tenant can be moved. It also shows
   what we get to skip by keeping code on the developer's machine.
4. **Our ACP bet looks better after reading their harness directory.** Four
   vendor integrations, one of them an HTTP server discovered by scraping
   stdout, versus one protocol and a pinned catalogue. Worth remembering the
   next time someone proposes integrating an agent natively "just this once".

## Not looked at

The web UI and its "web apps" feature, skills/skill-packs, crons and watches,
the `reach` mechanism for cross-scope work, and the classification/policy
layers. Any of them may hold better ideas than the five above; this was a
half-day read aimed at Slack, harness and hosting.
