# Spike: roles — where a "virtual employee" is stored, and how it runs

**Date:** 2026-08-06. **Sources:** qm read from a clone at commit `0f0e0ad`
(paths below are relative to its root; the decisive lines were re-verified
against the clone before this was written); Claude Code agent and skill files
present on this machine; Farol's own code. **Question:** if a team is to get a
"QA engineer" or a "support analyst", where does that thing live, how is it
launched, and what does it buy?

## The finding that reframes the question

**qm has no role object. The role is the scope.** `grep -rn persona src` returns
three hits, all of them the word *personal* inside a scope kind or helper
(`types.ts:12`, `:25`, `wiring.ts:1231`). There is one bot; what changes between
contexts is the configuration it resolved into.

A scope is derived, never chosen (`src/resolution/resolution-service.ts:18-23`):

```ts
function scopeFor(conversation, actor): ScopeId {
  if (conversation.kind === "dm") return scopeId("personal", actor.id);
  const ref = conversation.channelRef ?? conversation.threadRef;
  if (conversation.kind === "group") return scopeId("group", ref);
  return scopeId("channel", ref);
}
```

Where you speak to it decides which hat it wears. No `@qm-analyst`, no
addressing syntax, no dispatcher.

## (a) Where it is stored

Per-scope rows, one table per axis. `src/resolution/config-store.ts` defines a
`Persisted*` interface for each, all shaped `{ scopeId, ...value }`:
`PersistedSoul` (`:23`) — the closest thing to a persona, a versioned audited
text blob with history; `PersistedCommandPolicy` (`:40`), `PersistedEgressPolicy`
(`:52`), `PersistedApprovalGrantModes` (`:48`), `PersistedBaseModel` (`:60` —
model, harness and effort are scope properties, not global).

Storage is DB rows behind a `DurableMap`: `wiring.ts:422-423` registers
`souls: artifactMap<PersistedSoul>("soul_configs")` and
`soulHistory: artifactMap<PersistedSoulRevision>("soul_history")`. Not files,
not YAML.

The distributable half is files: skills are `SKILL.md` with `name` +
`description` frontmatter plus bundled data, fetched from git packs
(`src/skills/skill-pack-store.ts`: `{ url, ref, syncMode: "pinned"|"tracked",
trustTier, targetScopeId, subset }`) with SSRF defence and byte caps in
`pack-fetcher.ts`, and a collision check that refuses an import which would
clobber claimed paths.

**So: rows for what is edited at runtime, files for what is authored and
shipped.** qm's answer to "which one" is to fetch the files into rows.

## (b) How it is launched

Nobody routes. The mechanism is `resolve()`
(`resolution-service.ts:27-98`), per turn:

1. **Layers** — a stacked filesystem: the org scope read-only, the current
   scope read-write, and for a DM the actor's teams read-only.
2. **SOUL composition** — org text and scope text concatenated with an explicit
   fence: *"Lower-scope instructions (may add to, but MUST NOT override, the
   organization policy above)"*. Note the precedence is enforced **in prose to
   the model**, not structurally — a real weakness worth knowing before copying.
3. **Policy composition** — `composePolicy(orgPolicy, scopePolicy)`, and egress
   floors computed from *who is in the room* (`audienceEgressFloor`), so a guest
   joining tightens the agent mid-conversation.

The orchestrator then assembles the system prompt in a fixed order
(`src/core/orchestrator.ts:800`) — mode frame, resolved SOUL, shared core,
security policy, memory lines, sandbox block, **skills index**, gateway context,
cron menu, and the clock last. `stableSystemBytes` is measured at `:861`:
everything before the clock is prefix-cacheable. The ordering is deliberate.

Skill selection is model-driven: the index injects names and descriptions only,
and the model reads the body when it wants it. Two mechanisms are worth
stealing — **shadowing** (a narrower scope's skill of the same name overrides a
broader one, and the index line says so) and **availability gating**
(`filterConnectorSkills` hides skills whose connector is not configured, so a
skill that cannot work is never advertised).

The UX for creating a role is therefore *a conversation*: `mode-autonomous.md`
tells the agent that "from now on…" is an **edit to durable guidance**, to be
written back through the `guidance` tool — which is the SOUL write path.

## (c) Identity in Slack

qm tried the named-colleague route and stopped after one.
`src/slack/index.ts:48-61`:

```ts
const IDENTITY_TOKENS: Record<string, string | undefined> = { copilot: cfg.copilotBotToken };
function clientForIdentity(identity: string): WebClient {
  const token = IDENTITY_TOKENS[identity];
  if (!token) throw new Error(`no token for post identity "${identity}" (set its *_BOT_TOKEN env)`);
```

A second named agent means a second Slack app with its own bot token, wired in
by hand. It did not generalise. The cheap alternative also present —
`botIdentityFromEnv` in `src/slack/delivery.ts:20-44`, per-message `username`
and `icon_emoji` (the `chat:write.customize` scope) — is set once at boot and
never varied per turn.

The asymmetry is the whole story: a custom username changes how a message
*renders*, but does not create a mentionable entity. `@analyst` will not
autocomplete, and inbound mentions still arrive as one bot user id.

## (d) What it composes with, and what breaks at ten

**Memory bleed is solved cheaply** and we should take the answer wholesale —
`src/memory/policy.ts` is 35 lines: write to exactly one scope, read from the
layer stack (`writableMemoryScope`, `recallMemoryScopes`), and disclose
provenance in the prompt — a memory tagged *(said in …)* applies only if the tag
matches here.

**Permission sprawl** is met with an unoverridable org floor composed (not
replaced) by the scope, plus floors derived from the audience rather than
authored per role.

**Idle cost** is near zero because roles are inert text until selected — an
unselected skill costs one index line — and scheduled work is a queue
(`CronStore.due(now)` with optimistic slot claiming), not a running process.
Scheduling carries an authority knob, `runAs?: "owner" | "scopeFloor" |
"scopeShared"` (`types.ts:225`), and recipient consent is modelled explicitly:
you cannot schedule a bot to DM a colleague who has not accepted.

## What this changes for Farol

**Roles must not own sessions.** This is our sharpest exposure and it is worse
than qm's: an ACP session is a live process on somebody's laptop, and BYOA means
on the *mention author's* laptop. Ten roles that each hold a session are ten
agent processes on one machine. The Chat (thread) owns the ACP session; a role
is prompt and policy material applied to a turn.

**The pieces are already here.** `Chat.agent` exists and the cloud honours it
(`chat_router.py:251` — `agent=chat.agent or (runner.agents[0] …)`); we simply
never set it. The runner derives a per-channel working directory, and the
adapter under us reads `CLAUDE.md`, `SKILL.md` and `.claude/agents/*.md` from
it — so **materialising role files into the workspace before the session starts
makes roles work with no protocol change**. The SDK beneath the adapter also
exposes `systemPrompt`, an `agents` map (`description`, `prompt`, `tools`) and
`allowedTools`; our `session/new` sends only `cwd` and `mcpServers`, so passing
a role through the session — rather than through files the agent can rewrite —
is a small, well-defined extension.

**Our memory model is one layer short.** The gateway scopes a task token to
`viking://resources/slack/{channel}/`. A role that should see org-wide standing
facts *plus* its own channel has nowhere to put the former. A read-only org
layer in the scope check is the missing piece, and qm's recall/capture split is
the shape to copy.

**Named colleagues are a separate product decision**, and Slack bills for it in
OAuth installs. The cheap path — one bot, hats derived from where the mention
landed — costs us almost nothing, because we already route per channel, already
derive a folder per channel, and already scope memory per channel.
